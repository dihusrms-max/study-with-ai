# RAG 기초: 임베딩과 벡터 데이터베이스

## RAG란?

RAG는 Retrieval-Augmented Generation의 약자로, LLM이 답변하기 전에 관련 문서를 검색하고 그 내용을 근거로 답변하게 하는 구조다.

일반적인 LLM 호출은 다음과 같다.

```text
질문 → LLM → 답변
```

RAG는 중간에 검색 단계가 추가된다.

```text
질문 → 관련 문서 검색 → Context 구성 → LLM 답변
```

## 왜 RAG가 필요한가?

LLM은 학습 이후의 최신 정보나 사내 문서를 알지 못할 수 있다. 또한 근거가 없는 내용을 사실처럼 생성할 수 있다. RAG는 질문과 관련된 외부 문서를 찾아 Prompt에 제공하여 이 문제를 줄인다.

RAG의 주요 효과는 다음과 같다.

- 환각 감소
- 최신 문서 활용
- 사내·전문 문서 활용
- 답변 근거와 출처 제시

## 임베딩 기반 검색

임베딩은 문장의 의미를 숫자 벡터로 변환하는 작업이다.

```text
문서: "가계대출 금리 정보"
        ↓
벡터: [0.12, -0.43, ...]
```

질문도 같은 임베딩 모델로 벡터화한 뒤, 문서 벡터와의 유사도를 계산한다. 유사도가 높은 문서를 상위 결과로 선택한다.

학습에서는 `text-embedding-3-small`과 코사인 유사도를 사용했다.

## 벡터 DB의 역할

문서가 많아지면 모든 문서 벡터를 매번 직접 비교하기 어렵다. 벡터 DB는 임베딩 벡터를 색인하여 유사한 문서를 빠르게 찾는다.

학습한 도구는 다음과 같다.

- ChromaDB: 로컬에서 쉽게 시작할 수 있는 벡터 DB
- Qdrant: 벡터와 Payload를 함께 관리
- HNSW: 그래프 기반 근사 최근접 검색 방식

문서를 저장할 때는 본문뿐 아니라 제목, 카테고리, 출처 URL 같은 메타데이터도 함께 저장해야 한다.

## 메타데이터 필터링

벡터 유사도 검색에 조건을 추가할 수 있다.

```python
collection.query(
    query_texts=[question],
    n_results=3,
    where={"카테고리": {"$eq": "경제"}}
)
```

이렇게 하면 질문과 의미가 비슷하면서 특정 카테고리에 속한 문서만 검색할 수 있다. 본문에 특정 단어가 포함된 문서를 찾을 때는 `where_document`를 사용할 수 있다.

## 학습한 전체 구조

```text
문서 수집
→ 전처리·청킹
→ 임베딩 생성
→ 벡터 DB 저장
→ 질문 임베딩
→ 유사 문서 검색
→ 검색 결과를 Prompt에 삽입
→ LLM 답변 생성
```

## 정리

RAG에서 LLM은 검색을 직접 수행하는 것이 아니라, 검색 시스템이 찾아준 Context를 바탕으로 답변을 생성한다. 따라서 좋은 RAG를 만들려면 임베딩 모델뿐 아니라 문서 정제, 메타데이터 설계, 검색 조건, Context 구성까지 함께 관리해야 한다.
