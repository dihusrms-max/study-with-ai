# 대회 데이터는 모델 실행 전에 먼저 검사해야 한다

## 들어가며

대회에서는 모델의 성능만큼 입력 데이터와 제출 형식을 정확히 이해하는 일이 중요하다. 파일 형식이나 컬럼 수가 맞지 않으면 좋은 예측을 만들고도 제출에 실패할 수 있다.

## 압축 파일 구성 확인

대회용 ZIP에는 JSONL GZIP, CSV, JSON, TXT처럼 서로 다른 파일이 함께 들어 있을 수 있다. 따라서 전체 파일 목록과 형식을 먼저 확인하고, 형식에 따라 검사 방법을 나누어야 한다.

검사 결과에서는 파일 수와 형식, CSV의 shape와 컬럼, 자료형과 결측치, 중복 행과 문자열 공백, JSONL의 top-level key와 레코드 수를 기록한다.

## JSONL 데이터의 분석 단위

JSONL에서는 한 줄이 하나의 입찰공고 레코드에 해당한다. `id`의 결측·중복 여부를 확인하고, 중첩된 `docs`, `meta`, `input_completeness` 구조도 점검해야 한다.

문서 개수와 문서 type이 레코드마다 다를 수 있으므로, 모델 입력을 만들 때 어떤 문서를 포함할지 기준을 정해야 한다.

## 제출 형식 검증

`dev_labels.csv`와 `sample_submission.csv`를 비교하면 제출 파일의 기본 구조를 확인할 수 있다.

```text
id 보존
행 수 일치
컬럼 수와 컬럼명 일치
v1~v24 값 범위 확인
e1~e24 근거 문구 형식 확인
```

라벨이 없는 학습 데이터는 정답 데이터로 간주하지 않고 탐색이나 추론 대상으로 구분해야 한다.

## 재현 가능한 작업 공간

```text
data/raw        원본
data/processed  전처리 결과
notebooks       탐색과 실험
src             재사용 코드
outputs         예측과 제출 파일
logs            실행 전후 기록
tests           검증 코드
```

원본은 직접 수정하지 않고, 제출 파일은 버전을 붙여 저장한다. 실행 전후 행 수, 컬럼 수, 결측치 변화와 값 범위를 로그로 남기면 오류 원인을 다시 추적할 수 있다.

## 마무리

대회 데이터 검사는 단순한 전처리 전 단계가 아니라 데이터의 분석 단위와 신뢰성을 확인하는 품질 관리 과정이다. 모델을 개선하기 전에 입력 구조와 제출 계약을 자동으로 검증하는 것이 안전한 출발점이다.
