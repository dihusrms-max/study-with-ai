## 오늘 새롭게 이해한 것

### 1. Plan and Execute Agent의 역할 분담

복잡한 요청은 Planner가 목표를 할 일 목록으로 나누고, Executor가 각 항목을 도구로 처리하며, Replanner가 실행 결과에 따라 계획을 조정하는 흐름으로 다룰 수 있다. 할 일 목록을 눈에 보이게 유지하면 진행 상황과 다음 작업을 추적하기 쉽다. 모든 요청에 계획을 만들기보다, 간단한 요청은 건너뛰도록 시스템 지침을 설계하는 것도 중요하다.

Plan and Execute 노트북에서는 `TodoListMiddleware`를 사용해 할 일 목록을 관리하는 방법을 살펴봤다. CCTV 비교 요청에서는 분야별 FAQ 검색과 최종 Markdown 저장을 도구로 분리했다. 검색 결과를 바탕으로 보고서를 만든 뒤 저장하는 다단계 요청이라, 한 번의 응답보다 작업 단계와 도구를 명시하는 방식이 적합했다.

### 2. ReAct Agent의 도구 호출과 안전장치

ReAct는 Thought(판단) → Action(도구 호출) → Observation(실행 결과 확인)을 반복해 답을 만드는 구조다. `create_agent`에 모델과 도구를 등록하면 이 반복 호출 흐름을 구성할 수 있다. 도구는 함수뿐 아니라 이름·설명·입력 형식도 모델이 선택에 활용하므로, 각 도구의 목적과 입력 설명을 분명히 해야 한다.

병렬 도구 호출 실습에서는 도시별 날씨처럼 서로 독립적인 조회를 동시에 수행하고, 조회가 끝난 뒤 평균 계산처럼 앞선 결과에 의존하는 작업을 이어서 실행했다. 따라서 모든 도구를 무조건 병렬화하는 것이 아니라, 작업 사이의 의존성을 보고 병렬과 순차 단계를 나누는 것이 핵심이다.

미들웨어 실습에서는 도구 오류 처리와 모델 호출 횟수 제한을 통해 잘못된 응답이나 반복 호출이 계속되지 않도록 통제하는 방법을 살펴봤다. 사람 승인이 필요한 도구는 `HumanInTheLoopMiddleware`의 인터럽트와 체크포인터를 함께 사용해 승인 전 일시 중단하고 같은 대화 상태에서 재개하는 패턴을 확인했다.

## 아직 확인하거나 복습할 것

- 요청 난이도에 따라 계획을 만들거나 생략하는 기준을 실제 사례로 더 점검한다.
- 승인 인터럽트 뒤 도구 실행이 재개되는 흐름과 거절 시 처리를 실제 실행 결과로 확인한다.
- CCTV 보고서의 근거가 된 FAQ 내용을 최신 법령·지침과 대조한다. 노트북 산출물만으로 현행 법적 요건을 확정하지 않는다.
- 오류 처리와 호출 횟수 제한이 도구 실패 및 반복 호출 상황에서 최종 응답을 어떻게 바꾸는지 사례별로 확인한다.
