# 2026-09-11 일일 학습 보고

## 오늘 새롭게 이해한 것

- 대회 데이터는 모델을 실행하기 전에 파일 구성, 형식, 행 수, 컬럼, 자료형, 결측치, 중복을 먼저 확인해야 한다.
- ZIP 내부에는 JSONL GZIP, CSV, JSON, TXT 등 여러 형식이 함께 있을 수 있으므로 파일별 검사 방법을 구분해야 한다.
- JSONL 데이터에서는 한 줄이 의미하는 분석 단위와 `id`의 결측·중복 여부를 먼저 확인하고, 중첩된 `docs`와 `meta` 구조도 함께 점검해야 한다.
- `dev_labels.csv`와 `sample_submission.csv`를 비교하면 제출 파일의 컬럼 구조와 필요한 출력 형식을 확인할 수 있다.
- 데이터 검사와 전처리·모델 실행을 분리하면 원본을 보존하면서 문제를 조기에 발견할 수 있다.
- 대회 작업에서도 실행 전후 행 수, 컬럼 수, 결측치 변화와 제출 값 범위를 기록해야 재현성과 검증 가능성을 확보할 수 있다.
- 분석 프로젝트는 원본(`raw`), 전처리 결과(`processed`), 실험 Notebook, 재사용 코드, 결과물(`outputs`), 로그와 테스트를 분리하면 데이터 흐름과 책임 범위를 관리하기 쉽다.
- Python 버전과 패키지, Jupyter 커널을 프로젝트 단위로 고정하면 사람마다 다른 실행 환경에서 발생하는 오류를 줄일 수 있다.
- 개인 환경·서버 환경·GPU 환경을 한꺼번에 구성하지 않고, 기본 실행 환경을 먼저 검증한 뒤 다음 환경을 단계적으로 확장해야 한다.

- 패키지 설치, Python 버전, Jupyter 커널, import 검증을 자동화해 새 환경에서도 재현하는 방법.

## 직접 해본 것

- 대회용 `open.zip`을 원본 변경 없이 읽기 전용으로 검사했다.
- ZIP 내부 파일 수와 형식을 확인하고 JSONL GZIP, CSV, JSON, TXT 파일을 구분했다.
- 주요 CSV의 shape, 컬럼, dtype, 결측치, 중복 행, 문자열 공백 여부를 확인했다.
- `test.jsonl.gz`, `dev.jsonl.gz`, `train_unlabeled.jsonl.gz`의 행 수와 top-level key, `id` 중복, `docs` 개수 범위를 비교했다.
- `dev_labels.csv`와 `sample_submission.csv`의 49개 컬럼 구조를 확인하고 제출 형식 검증 항목을 정리했다.
- 대회 작업 공간의 `data/raw`, `data/processed`, `outputs`, `logs`, `tests` 역할과 원본 보존·버전별 제출 파일 관리 원칙을 정리했다.
- VS Code Jupyter에서 대회 전용 커널을 선택하고 실행 환경을 확인해야 하는 이유를 점검했다.
- 개인 작업환경 설치 가이드의 단계적 구성(기본 OS·개발 도구 → Python·패키지 → Jupyter → 최소 검증)을 검토했다.
- `pandas`, `numpy`, `scikit-learn`, Jupyter, pytest, ruff처럼 분석·검증에 필요한 도구를 역할별로 구분하고, GPU·서버 환경은 후순위로 분리했다.

## 오늘의 핵심 인사이트

- 대회에서는 높은 점수보다 먼저 입력 데이터와 제출 형식이 정확한지 검증해야 한다. 작은 형식 오류도 전체 결과를 무효화할 수 있다.
- 데이터 검사는 단순한 전처리 전 단계가 아니라, 데이터의 분석 단위와 신뢰성을 확인하고 다음 작업의 위험을 줄이는 품질 관리 단계다.
- 재현 가능한 분석은 코드만 잘 작성하는 문제가 아니라, 데이터 위치·환경·실행 방법·검증 기준·기록 위치를 함께 설계하는 작업이다.
