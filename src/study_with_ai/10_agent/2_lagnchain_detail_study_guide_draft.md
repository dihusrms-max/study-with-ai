# LangChain Detail 노트북 학습 가이드 초안

대상 노트북: `2_lagnchain_detail.ipynb`

## 1. 학습 목표

이 노트북의 코드를 통째로 암기하는 것이 목표가 아니다.

- RAG 애플리케이션의 전체 흐름을 설명한다.
- 각 변수의 입력과 출력을 추적한다.
- 코드를 보지 않고 전체 구조를 의사코드로 작성한다.
- 요구사항에 맞게 기존 코드를 수정한다.
- 오류 발생 지점을 단계별로 찾는다.

백지 코딩은 아무것도 참고하지 않고 모든 문법을 기억해내는 것이 아니다. 먼저 구조를 세우고, 필요한 문법은 문서와 기존 코드를 참고해 완성하는 것이다.

## 2. 전체 흐름

```text
환경변수와 라이브러리 설정
        ↓
PostgreSQL 연결
        ↓
Embedding 모델 준비
        ↓
PGVectorStore 연결
        ↓
사용자 질문 입력
        ↓
유사 문서 검색
        ↓
질문 + 검색 문서로 프롬프트 구성
        ↓
LLM 응답 생성
        ↓
대화 기록 저장 및 조회
```

## 3. 각 셀을 볼 때 답할 질문

```text
이 셀은 왜 필요한가?
입력값은 무엇인가?
출력값은 무엇인가?
출력값을 다음에 사용하는 코드는 무엇인가?
이 셀을 삭제하면 어디서 오류가 나는가?
다른 라이브러리로 대체할 수 있는가?
```

예를 들어 `store.similarity_search(question, k=4)`는 질문을 벡터로 바꾸고 유사한 문서 4개를 반환한다. 반환값은 `Document` 리스트이며, 본문은 `page_content`, 부가정보는 `metadata`에 있다.

## 4. 핵심 객체

| 객체 | 역할 |
|---|---|
| `embeddings` | 텍스트를 벡터로 변환 |
| `engine` | PostgreSQL 연결 |
| `store` | 벡터 저장소 및 문서 검색 |
| `Document` | 검색된 문서 표현 |
| `prompt` | LLM에게 전달할 지시문 |
| `chain` | 여러 처리 단계 연결 |
| `history` | 대화 기록 저장 및 조회 |
| `session_id` | 대화방 또는 사용자 구분 |

## 5. 학습 순서

### 1회차: 구조 파악

노트북을 실행하면서 각 셀 아래에 한 줄 설명을 적는다.

```text
이 셀은 환경변수에서 API 키를 불러온다.
이 셀은 PostgreSQL 연결 객체를 만든다.
이 셀은 embedding 모델과 vector store를 연결한다.
이 셀은 질문과 유사한 문서를 검색한다.
```

통과 기준:

- 각 셀의 역할을 설명할 수 있다.
- 주요 변수의 타입을 확인할 수 있다.
- 검색 결과의 본문과 metadata를 구분할 수 있다.
- 질문이 최종 응답으로 변하는 과정을 설명할 수 있다.

### 2회차: 변수 흐름 정리

| 단계 | 변수 | 입력 | 출력 | 다음 사용처 |
|---|---|---|---|---|
| DB 연결 | `engine` | DB URL | DB 엔진 | `store` 생성 |
| 임베딩 | `embeddings` | 텍스트 | 벡터 | 문서 검색 |
| 검색 | `question` | 사용자 질문 | 문자열 | `similarity_search` |
| 검색 결과 | `documents` | 질문 | `Document` 리스트 | 프롬프트 |
| 생성 | `answer` | 질문 + 문서 | 문자열 | 사용자에게 반환 |
| 대화 기록 | `session_id` | 대화 식별자 | 저장된 메시지 | 다음 응답 |

모르는 값은 `type()`, `print()`, `len()`으로 직접 확인한다.

### 3회차: 원본 없이 구조 복원

```python
# 환경변수와 라이브러리 준비
# PostgreSQL 연결
# Embedding 모델 생성
# Vector store 연결
# 사용자 질문으로 관련 문서 검색
# 검색 결과를 context로 변환
# 질문과 context를 prompt에 삽입
# LLM 호출
# 응답 반환
# 대화 기록 저장 및 조회
```

먼저 구조를 작성하고, 막히는 부분만 원본이나 공식 문서에서 확인한다.

### 4회차: 작은 단위로 재구현

1. 벡터 검색만 구현한다.
2. 검색 없이 LLM 호출만 구현한다.
3. 검색 결과를 LLM에 전달하는 기본 RAG를 구현한다.
4. 마지막에 대화 기록을 추가한다.

검색 기능과 대화 기록 기능은 먼저 따로 이해한 뒤 연결한다.

## 6. 변형 과제

### 쉬운 과제

- `k=4`를 `k=2`로 변경한다.
- 검색 결과의 제목만 출력한다.
- 검색 결과의 metadata만 출력한다.
- 사용자가 직접 질문을 입력하도록 변경한다.
- 답변과 함께 사용한 문서 제목을 출력한다.

### 중간 과제

- 검색 결과가 없을 때 별도 메시지를 반환한다.
- 특정 분야의 문서만 검색한다.
- 검색 문서 수를 설정값으로 분리한다.
- 질문, 검색 결과, 최종 응답을 모두 출력한다.
- 대화 기록을 제거한 단순 버전을 만든다.

### 어려운 과제

- 검색 결과와 대화 기록을 함께 프롬프트에 전달한다.
- 답변에 출처를 표시한다.
- 질문을 다시 작성한 뒤 검색한다.
- `k`, chunk 크기, embedding 모델의 영향을 비교한다.
- 다른 데이터셋에 같은 구조를 적용한다.

## 8. 외워야 하는 것과 외우지 않아도 되는 것

### 외워야 하는 것

- RAG 전체 데이터 흐름
- embedding과 vector store의 역할
- `Document`의 본문과 metadata
- 질문과 context의 관계
- LLM 입력과 출력
- 대화 기록과 `session_id`의 관계
- 입력과 출력 타입을 확인하는 습관

### 외우지 않아도 되는 것

- 모든 import 경로
- 모든 LangChain 생성자 옵션
- DB 연결 문자열의 세부 형식
- 자주 쓰지 않는 메서드 이름
- 공식 문서에서 확인 가능한 설정값
