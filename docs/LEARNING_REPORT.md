# 학습 진행 분석 보고서

작성일: 2026-08-28

## 1. 학습 목표와 진행 흐름

이번 학습은 단순 자기소개 페이지에서 시작해, 여러 기능 페이지를 추가하고 Git/GitHub로 변경 이력을 관리하는 흐름으로 확장되었습니다.

주요 흐름은 다음과 같습니다.

1. HTML, CSS, JavaScript 기반의 정적 자기소개 페이지 구성
2. 프로필 이미지와 실제 문구를 반영하고 디자인 방향 조정
3. GIF 편집기, 미니 축구 게임, 이상형 월드컵 등 독립 기능 페이지 추가
4. UI/UX 문제를 검토하고 개선 방향을 승인 기반으로 결정
5. Git 설치, VS Code Source Control, Graph, 커밋과 Push 학습
6. `.gitignore`를 추가하고 GitHub 원격 저장소까지 동기화

## 3. Git/GitHub 학습 평가

### 잘 수행한 부분

- Git을 설치하고 VS Code에서 저장소 변경사항을 확인했습니다.
- `Changes`에서 파일을 스테이징하고 커밋을 만들었습니다.
- Graph에서 로컬 커밋과 GitHub 원격 브랜치의 위치 차이를 확인했습니다.
- `Sync Changes`를 통해 `main`과 `origin/main`을 동기화했습니다.
- `.gitignore`를 커밋해 팀/다른 환경에서도 같은 제외 규칙을 공유할 수 있게 했습니다.

### 핵심 개념 이해

| 개념 | 현재 이해 수준 | 설명 |
| --- | --- | --- |
| Changes | 이해함 | 아직 커밋하지 않은 파일 목록 |
| Staged Changes | 이해함 | 다음 커밋에 포함하도록 선택한 파일 목록 |
| Commit | 이해함 | 변경을 로컬 Git 기록으로 저장 |
| Push / Sync | 이해함 | 로컬 커밋을 GitHub에 동기화 |
| Graph | 이해함 | 커밋 역사와 로컬/원격 위치를 시각적으로 확인 |
| `.gitignore` | 이해함 | 자동 생성물·비밀값 등을 Git 관리에서 제외 |

### 보완할 부분

- `README.md`가 UTF-16으로 저장되어 Git에서 텍스트 대신 Binary 변경으로 표시됩니다. 다음 수정 시 UTF-8로 저장하는 연습이 필요합니다.
- 커밋 메시지는 `test`보다 `Add .gitignore`처럼 변경 의도가 드러나게 작성하는 습관이 좋습니다.
- `Discard Changes`, `Reset`, `Rebase`, `Force Push`는 파일이나 기록을 되돌릴 수 있으므로 현재 단계에서는 사용하지 않는 것을 권합니다.

## 4. 개발 방식에서 배운 점

### 승인 기반 작업 흐름

기능을 바로 추가하기보다 다음 순서로 진행했습니다.

`기능 제안 → 선택지 확인 → 승인 → 구현 → 검증 → 결과 보고`

이 방식은 요구사항이 바뀌는 상황에서 불필요한 작업을 줄이고, 구현 전에 화면과 범위를 합의하는 데 효과적입니다.

### 기능을 작게 나누는 방법

- GIF 편집기는 먼저 “업로드와 UI 검증”만 되는 프로토타입으로 시작했습니다.
- 실제 GIF 재인코딩과 다운로드는 복잡도가 높으므로 다음 단계로 분리했습니다.
- 게임과 월드컵은 각 페이지가 독립적으로 실행되도록 만들어, 기능 간 영향 범위를 줄였습니다.

## 5. 현재 프로젝트 개선 권장사항

우선순위 순서입니다.

1. `README.md`를 UTF-8로 저장하고 프로젝트 소개·실행 방법을 작성합니다.
2. 루트의 `카리나.jpg`와 `images/karina.jpg` 중 중복된 루트 파일을 제거합니다. 웹페이지는 `images/karina.jpg`만 사용합니다.
3. GIF 테스트 페이지의 파일 교체, 입력값 검증, 옵션 상태 안내를 개선합니다.
4. 공통 헤더를 여러 HTML 파일에 반복하지 않도록 구조를 정리합니다. 정적 페이지 학습 후에는 컴포넌트/템플릿 도구 도입을 검토할 수 있습니다.
5. Git 커밋을 기능 단위로 작성하고, 매번 Push 전 Changes와 Graph를 확인합니다.
