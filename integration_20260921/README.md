## 확인된 문제와 통합 전 조치

1. **팀원 이어 실행 실패 — 재현 완료.** `script.py:899`에서 CSV로 읽은 v 값은 문자열인데 `validate_rows`(`script.py:843`)는 정수만 허용한다. 동일 출력 경로로 두 번째 실행 시 `ValueError: Non-binary output flag`가 발생했다. 체크포인트 로딩에서 형식 검증 및 정수 변환이 필요하다. 입력·코드·설정 해시가 맞는 체크포인트만 이어 쓰도록 보강하는 것도 권장한다.
2. **API 어댑터의 외부 파일 누락 — 정적 확인.** `run_api.py`는 `root.parents[1]/baseline/p003_script.py`의 `ApiRunner`를 로드하지만 해당 파일은 ZIP에 없다. API 평가를 연결하려면 이 의존성을 명시적으로 공급하거나 프로젝트의 공통 러너로 교체해야 한다. 현재 자료만으로 API 평가가 준비됐다고 볼 수 없다.
3. **실패 건 건너뛰기에서 청크 전체 누락 가능 — 정적 확인.** 팀원 `run(..., skip_failures=True)`는 청크에 실패 건이 하나라도 남으면 `continue`하여 같은 청크의 성공 건도 저장하지 않는다(`script.py:948–960`). API 옵션 경로의 문제이며 기본 제출 경로는 실패 시 예외를 낸다. 건별 성공 결과를 저장하도록 수정해야 한다.
4. **규칙 보정은 성능 검증 대상.** 팀원 mock은 모든 모델 판정을 0으로 반환하지만 최종 결과에는 3건 합계 3개의 양성 판정이 생겼다. 이는 후처리 규칙이 판정을 바꾼다는 실행 증거이며 정확도 개선의 증거는 아니다. 검색만 적용한 후보와 규칙까지 적용한 후보를 구분해 비교해야 한다.
5. **근거 없는 양성 처리 정책이 분리되어 있음.** `methodology_repair.py`는 근거 없는 비부재탐지 양성을 0으로 바꾸지만, 제출 `script.py`가 이를 호출하지는 않는다. 자동 통합하면 판정이 달라지므로 별도 실험 후보로 검증한다.
6. **개발용 도구와 제출 의존성 구분.** `render_validation_report.py`는 matplotlib을 사용하지만 제출 진입점은 이를 import하지 않는다. 팀원 README가 언급하는 `실행_제출_안내.md`도 ZIP에는 없다. 누락 문서를 제출 필수 코드로 오인하지 않는다.

## 권장 구현 순서

1. `sources/`를 보존한 채 별도 `candidate/`에서 사용자 진입점과 CLI를 기준으로 작업한다. 사용자 `requirements.txt`를 출발점으로 사용한다.
2. 팀원 `response_protocol.py`와 근거문구 검증을 연결한다. 응답 타입, 재시도, 실패 시 동작을 통일하고 무응답을 정상 판정으로 집계하지 않도록 한다.
3. `LawIndex`, `ProductCatalog`, 문서 선택 기능을 옵션으로 도입한다. `PromptBuilder`는 보조 모듈과 결합되어 있으므로 그대로 복사하기보다 사실 추출과 판정 덮어쓰기를 분리한다.
4. `decision_support.py`, `qualification_support.py`의 판정 덮어쓰기는 별도 옵션으로 둔다. 항목별 적용 전후 판정·근거·사유를 기록한다.
5. 이어 실행 타입 문제와 실패 청크 저장 문제를 수정하고, 동일 입력에서 신규 실행/중단 후 재개/실패 건 재시도 결과를 비교한다.
6. 같은 개발 데이터·정답 버전·모델·생성 설정으로 아래 후보를 평가한 뒤 채택한다.

| 후보 | 비교 목적 |
|---|---|
| A: 사용자 원본 | 기준 성능·시간 |
| B: 팀원 원본 | 받은 코드 그대로의 비교 기준 |
| C: 사용자 기반 + 응답·근거 검증 | 안정성과 근거 품질 변화 |
| D: C + 검색·문서 선택 | 검색 효과 |
| E: D + 규칙 보정 | 규칙별 성능 증감 |

평가 시 전체·항목별 지표, 근거 적합성, JSON 실패/복구 건수, 호출 수, 실행 시간, GPU 메모리를 함께 기록한다. 이 준비 단계에서는 모델/API 호출과 정확도 평가는 하지 않았다.
